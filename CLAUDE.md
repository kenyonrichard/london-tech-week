# London Tech Week 2026 — Fact-Finding Report

Personal presentation site by Richard Kenyon: results of a fact-finding mission to London Tech Week (8–10 June 2026). Static Jekyll site on GitHub Pages, published from `main` at https://kenyonrichard.github.io/london-tech-week/ (repo `kenyonrichard/london-tech-week`).

### Page conventions

- Each page starts with front matter: `layout: default`, `title` (full `<title>`), `description`, `root` (`""` for `index.html`, `"../"` for `pages/*`), `active` (nav highlight key).
- The page file contains only the body (sections), not `<html>`/`<head>`/header/footer.
- Header/footer links are built from `root` (`{{ include.root }}pages/x.html`).
- Image paths on pages are written relative to `root` (e.g. `../images/web/foo.jpg`).
- Layout appends `?v={{ site.time | date: '%s' }}` to CSS/JS URLs (cache-busting; see history below).

### Images and lightbox

- Pages display `images/web/NAME.jpg`; gallery/home strip display `images/thumbs/NAME.jpg`.
- The lightbox (built in `js/site.js` for any page with `.gallery-item` or `.carousel-slide`) derives the full image by rewriting `/images/(thumbs|web)/` to `/images/`, so **every displayed image needs an original of the same filename in `images/`**.
- Always give `<img>` `width`/`height` attributes (CSS controls the rendered size). First visible image on a page uses `fetchpriority="high"`; others use `loading="lazy"`.
- Gallery tiles and carousel slides use `role="button" tabindex="0"` (no inline `onclick`; handled by delegation in `js/site.js`). Carousel prev/next buttons still call global `slideTo(id, dir)`.
- Adding a photo: put the original in `images/`, make a 1600px-wide copy in `images/web/` (and a 480px thumb in `images/thumbs/` if it goes in the gallery), keep alt text and captions meaningful.

### CSS notes

- Alternating section backgrounds come from `section:nth-child(even)`, so adding/removing top-level `<section>` elements changes the striping.
- Legacy class names (`.img-placeholder`, `.carousel`) remain from earlier iterations — don't rename without checking all pages.
- Former inline styles now live in the "Classes replacing former inline styles" block at the end of the file (`img-cover`, `card-image-flush`, `highlights-*`, `floorplan-frame`, …). Prefer classes over inline styles.
- Only breakpoints: 768px (main), 480px (small type sizes). `:focus-visible` outline and `prefers-reduced-motion` rules exist.

## Audit log

### 2026-10-14 — performance, accessibility and SEO audit (PRs 3–5 merged to `main`)

Findings and what was done:

- **Heavy images** (pages loaded multi-MB originals) → resized copies in `images/web/`, originals kept for the lightbox, dimensions added.
- **38 MB autoplay video** → re-encoded to ~1.6 MB, poster added, paused for reduced-motion users.
- **Gallery/carousel lightboxes** were mouse-only and duplicated across four pages → one implementation in `js/site.js` with keyboard support, focus trap/return, `role="dialog"`, labelled buttons, per-image alt text, neighbour preloading.
- **Nav dropdown** → `aria-haspopup`/`aria-expanded`, Escape closes.
- **No SEO metadata** → description, canonical, Open Graph/Twitter tags, `robots.txt`, `sitemap.xml`.
- **Duplicated `<head>` and inline scripts/styles** → shared layout, `js/site.js`, CSS classes.
- **Mobile**: footer links didn't wrap, causing sideways scroll at 390px → fixed.
- **Cache incident:** after the first deploy, About/Event/VIP/Media looked broken because browsers served the old cached `style.css` against new HTML. Fixed by the `?v=` query strings. Remedy for similar reports: hard refresh, and check cache-busting is intact.
- `monogram.af` moved out of the published root.

Verified before merging: Jekyll build, text of every page compared against the pre-change version (identical apart from nav/footer), all header/footer links and asset references resolve, Playwright run (lightbox via keyboard, carousels, dropdown, no JS errors, no horizontal overflow at 390/900/1280px).

### Known remaining items (deliberately not done)

- CSS minification (needs a build step; saves a few KB).
- Git LFS / history shrink — the old 38 MB video and original images remain in git history; fixing needs history rewrite, only with explicit approval.
- Generating the gallery tiles from a `_data` file instead of hand-written HTML.
- `index.html` can overflow by ~1px at 390px width (cosmetic, unresolved).
- GitHub Pages runs an older Jekyll (3.x) than the 4.4 used for local testing — always confirm the Pages build succeeded after merging.

## How we work together

Working style that has been established in this repo:

1. **Review first, then act.** For "look at / improve the site" requests, inspect the code and report findings ranked by impact before changing anything; implement when the owner says to. Keep summaries short and plain; separate "done", "not done" and "things to be aware of".
2. **Never change content.** Improvements must be invisible to the text and photos. Anything visible (e.g. a footer note) is a content change and needs asking first. Notes "for the record" belong in this file, not on the site.
3. **Branch and PR workflow.** Work on the designated feature branch (currently `claude/eager-maxwell-8nvya5`). Never push straight to `main` — that was blocked as a production deploy. Open a PR, and **merge only when the owner explicitly says so** (e.g. "merge PR 5"). After a PR is merged, restart the branch from `origin/main` (`git checkout -B <branch> origin/main`) before new work.
4. **Commit and PR hygiene.** Clear commit messages; end commits with the attribution lines from the session; PR bodies follow the repo's/owner's format (no template exists) and end with the Claude Code attribution. Link PRs as full URLs.
5. **Verify before pushing.** Build with `jekyll build -d <tmp>` (Jekyll is installed via `gem install jekyll`; add the gem bin dir to `PATH`), check links/assets, and for UI/JS changes drive the built site with Playwright (Chromium at `/opt/pw-browsers/chromium`; call functions, not strings, in `$eval`). Compare page text against the previous version when claiming "no content change".
6. **After merging, check the deploy** with the GitHub Actions "pages build and deployment" runs (via the GitHub MCP tools). The live site cannot be fetched from the cloud session (proxy returns 403), so ask the owner to eyeball it, or to send a screenshot/console errors if something looks wrong.
7. **Be honest about limits.** If something couldn't be verified (live site, older Pages Jekyll), say so. If a cause is a hypothesis (e.g. stale cache), say it's a hypothesis and what would confirm it.
8. **Ask before large or irreversible steps** (history rewrite, deleting originals, big refactors such as the gallery data file). Offer them as options with a recommendation instead of doing them unprompted.
9. **Tool notes.** GitHub access is via the `mcp__github__*` tools only (no `gh` CLI) and is scoped to this repository. Temporary files go in the session scratchpad, not the repo.
